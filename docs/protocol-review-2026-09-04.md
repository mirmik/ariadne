# Проверка протоколов Ariadne, 2026-09-04

Исходная проверенная реализация: `40fe426479b65cfbb6e7c9f6672e9119dfe39905`.
Ниже сохранены результаты первоначального review. Последующим изменением
исправлены все пять воспроизведённых дефектов (#2174, #2176–#2179), а также
ограничен рост/перезапись registry (#2173). `protocol_review_test.go` теперь входят
в обычный набор без build tag. Для #2175 явно закреплена семантика: revoke
отзывает доступ, фоновые jobs отменяют отдельно до отзыва; это отражено в CLI,
MCP, документации и интеграционном тесте.

Исправление использует wire v2 / QUIC ALPN `ariadne/2`: старый протокол отклоняется
без fallback, relay и connector обновляются вместе. Identity и pins сохранены.
Истории поздних IDs ограничены 4096 элементами каждого типа; приём download
независимо ограничен 1 GiB по умолчанию (`--max-download-size` у CLI/MCP).

Результат: в проверенных сценариях подменить relay через OPAQUE/TLS или
повторно использовать подпись регистрации с новым challenge не удалось.
В исходной версии обнаружены пять воспроизводимых дефектов контракта/машины состояний,
один из которых уже известен (#2174). Это не доказательство отсутствия иных
уязвимостей и не независимый аудит криптографических примитивов.

## Модель угроз и метод

Проверялись сетевой посредник при первом сопряжении, подмена сообщений,
повтор handshake, конкурирующие завершения pairing, злонамеренный node,
опоздавшие ответы и корректный connector после изменения alias.
Исследованы OPAQUE glue, pinning/redial, Ed25519 registration, QUIC framing,
разделение management/node plane, SSH stream authorization, exec/job correlation
и файловый протокол. Тесты локальные; чужие и рабочие удалённые машины не трогались.

По текущему контракту relay доверенный: он авторизует команды, сообщает
connector одноразовый SSH client key и сообщает CLI ожидаемый SSH host key.
Компрометация relay находится внутри этой границы доверия. SSH шифрует payload
от добросовестного транспортирующего relay, но независимой защиты от активно
злонамеренного relay в zero-config shell нет. Exec и файлы relay видит открытыми
после завершения TLS. SHA-256 файла проверяет согласованность переданных bytes,
а не независимую аутентичность источника.

Сопоставление с источниками:

- [RFC 9807, §9.2](https://www.rfc-editor.org/rfc/rfc9807.html#section-9.2):
  online guessing возможен с обеих сторон, а отсутствие KE3 нужно считать
  неудачной попыткой. Ariadne расходует серверную попытку до KE2 и ограничивает
  использование кода клиентом на каждом endpoint.
- [RFC 9807, §10.3](https://www.rfc-editor.org/rfc/rfc9807.html#section-10.3):
  стороны должны согласовать identities. Здесь OPAQUE identities — фиксированные
  роли, а прикладная node identity дополнительно включена в финальный HMAC.
- В установленном `github.com/bytemare/opaque@v0.18.0/README.md` прямо написано,
  что библиотека не проходила независимый аудит. DefaultConfiguration использует
  Ristretto255/SHA-512 и Argon2id. [Исходный release](https://github.com/bytemare/opaque/tree/v0.18.0).
  Проверка происхождения release-аттестаций и side-channel свойств в этот review
  не входила. После исправлений выполнен govulncheck по актуальной базе: результат
  и ограничение проверки приведены ниже.

## Подтверждённые дефекты

| Карточка | Оценка в текущей модели | Результат проверки |
|---|---|---|
| #2178 | Средняя, истощение ресурсов при запрошенном download | Растущий файл обходит `MaxFileBytes`; принимающий client не имеет своей byte quota |
| #2177 | Средняя, доступность активной node-сессии | Нормальный поздний exec/job response становится fatal protocol error |
| #2179 | Средняя, функциональная доступность | Подтверждённый alias, отличный от reported alias, ломает reconnect |
| #2176 | Низкая, срок действия commissioning | KE3 принимается после expiry окна, если KE1 успел раньше |
| #2174 | Низкая при защищённом TLS; дефект целостности transcript | Изменение Capabilities не нарушает Ed25519 signature |

### #2178: лимит скачивания проверяется до потока, а не во время него

`internal/connector/file_stream.go:runFileDownload` сравнивает только исходный
`stat.Size()` с MaxFileBytes. В цикле чтения накапливается size, но сравнения с
лимитом уже нет. Тест начинает с файла в один байт, после `stream.opened`
дописывает два байта в тот же inode и получает три переданных байта при лимите 1.
Это детерминированный тест TOCTOU, не попытка заполнить диск.

Дополнительно `internal/client/client.go:DownloadFile` пишет все приходящие
data frames без независимого максимума. Компрометированный выбранный node может
отправлять поток до отмены/дедлайна/исчерпания диска MCP host. Для этого management
сторона должна сначала запросить download у этого узла: неизвестный node не может
сам открыть поток. Недостающая client quota установлена чтением кода, отдельный
тест заполнения диска не выполнялся.

Исправление: проверка накопленного размера до отправки и до записи очередного
chunk, локальный лимит клиента независимо от метаданных node, явная ошибка и
очистка временного файла. SHA-256 в конце потока эту угрозу не ограничивает.

### #2177: поздние ответы после cancellation отключают весь connector

`internal/relay/session.go:exec` и `job` удаляют ID из pending при выходе по
контексту. Connector может корректно ответить после этого, например завершив
отменённый процесс. `handleControl` считает такой ответ unsolicited и возвращает
ошибку; `run` завершает node-сессию, и unregister закрывает другие потоки.

Тест вызывает настоящие методы выдачи запросов, даёт им выйти по отменённому
контексту, затем доставляет ответ на фактически отправленный ID. Оба варианта
дают fatal error. Это проверка перехода состояния, не полноценный нагрузочный
тест сетевой гонки.

Нужна ограниченная история ранее выданных/отменённых ID или явный протокол
завершения отмены. Не следует просто разрешать любые unsolicited responses.
История `known` для stream IDs в исходной версии тоже сохранялась до конца сессии без
очистки; при проектировании истории requests стоит сразу определить границы
удержания и поведение очень поздних сообщений.

### #2179: registration response смешивает reported и claimed alias

`internal/relay/server.go:register` восстанавливает ClaimedAlias и возвращает
его в `relay.registered`. `internal/connector/connector.go:RunOnce` требует
точного равенства возвращённого Alias с Alias исходного hello.

Настоящий relay и connector через net.Pipe воспроизводят:
reported `original`, claim `grandma`, reconnect →
`relay registered a different node identity`.
То же возможно после смены hostname, если он используется как reported alias.

Нужно разделить проверку неизменяемых NodeID/SSHHostKey и изменение доверенного
имени. Ослаблять проверку собственно ключа/identity ради alias нельзя.

### #2176: expiry не проверяется на commit pairing

`internal/pairing/pairing.go:Begin` проверяет срок; `Finish` вызывает `consume`,
который проверяет лишь наличие active и generation. Тест переводит deadline в
прошлое между KE2 и KE3; сервер всё равно выдаёт аутентифицированный pin.

Это не получение доступа без кода. В настоящем relay общая длительность handshake
ограничена RegistrationTimeout, по умолчанию 10 секунд, поэтому окно нельзя
продлевать бесконечно удержанием соединения. Но заявленный deadline не строгий.
Нужно атомарно проверять срок вместе с расходованием окна и покрыть границу TTL.

### #2174: capabilities не входят в подпись

`internal/wire/protocol.go:RegistrationTranscript` включает challenge, NodeID,
Alias, PublicKey, SSHHostKey, Platform, Architecture, ConnectorVersion, но
пропускает Capabilities. Тест меняет каждое поле отдельно: все перечисленные
поля и challenge защищены, capabilities меняются без нарушения подписи.

При аутентифицированном TLS обычный сетевой посредник всё равно не может менять
hello. Здесь подтверждено расхождение с заявленным «все поля hello», а не
самостоятельный remote-code-execution. Добавлять поле в transcript нужно вместе
с явным решением о совместимости старых connector и protocol version.

## Что выдержало проверки

- TLS-посредник с отдельным сертификатом прозрачно пересылает все сообщения
  OPAQUE настоящему relay. Connector сохраняет pin настоящего relay, закрывает
  первую сессию, а повторный TLS к посреднику падает именно на pin mismatch.
  Посредник получает только один application connection, commissioning.
- Посредник меняет только финальный certificate pin, сохраняя прежний MAC:
  клиент отвергает binding, trust store не получает pin.
- Два валидных конкурирующих Finish одного окна дают ровно одного победителя.
- Новый `Open` делает завершение старой generation недействительным.
- KE3 одной сессии не принимается во второй сессии, даже при повторе KE1.
- Изменение challenge и подписанных полей hello делает прежнюю signature
  недействительной. SSH host key также покрыт.
- Существующие тесты wrong code, attempts/TTL на Begin, привязки HMAC к node/pin,
  неизвестных сообщений, framing limits, разделения management/node plane,
  SSH/QUIC integration и смены сертификата проходят.
- QUIC Config явно отключает 0-RTT и ограничивает входящие streams; length framing
  проверяет максимальный размер до выделения payload. Это подтверждено чтением
  конфигурации и существующими тестами, не QUIC-fuzzing или проверкой UDP flood.

## Существенные границы вывода

Pairing удостоверяет relay для connector, но не является admission control
для публичного registry. В исходной версии #2173 позволял неограниченно накапливать
identities; после исправления действуют квота и rate limit, но возможность
посторонним занять публичную квоту сохраняется. Окно на пять попыток также
можно исчерпать отказами чужих клиентов: это DoS commissioning, не угадывание кода.

Фиксированная OPAQUE client identity и финальный server-to-client HMAC означают,
что доказательство прикладной node identity следует интерпретировать осторожно.
Подпись внешнего KE1 доказывает владение ключом подписанта, но сама по себе не
доказывает, что подписант создал KE1 или знает pairing-код. Финальная проверка
node_id на клиенте защищает его pin binding. Нельзя без дополнительной привязки
превращать серверный факт получения KE3 в enrollment/claim указанного node_id.
Это анализ конструкции; отдельная атака замены внешней identity не воспроизводилась.

Проверка не подтверждает защиту от скомпрометированного relay, локального процесса
с тем же OS UID, ошибок агента, supply-chain атак и всех вариантов исчерпания
ресурсов. Истечение pairing не отзывает уже сохранённое доверие. Revoke identity
не равен остановке всех фоновых jobs (#2175).

Для текущего личного экспериментального развёртывания нет результата теста,
требующего отказаться от схемы OPAQUE → pin → redial. Оснований объявлять её
полностью проверенной для production тоже нет: остаётся отдельное решение по
библиотеке и криптографическому аудиту (#2141).

## Как повторить

Обычные тесты, включая integration на локальных TCP/UDP sockets:

```sh
go test -race -count=1 ./...
```

Результат: PASS. Нужна среда, разрешающая loopback listeners; первоначальная
попытка нового MITM-теста внутри sandbox была запрещена, после чего прогон
выполнен с разрешением сокетов.

Также PASS: `go vet ./...`, `go build ./...` на Linux; кросс-сборки
Windows/amd64 connector, MCP и relay, Android/arm64 connector и CLI с CGO=0.
Общая Windows-сборка `./cmd/...` не поддерживается: независимый ssh-breakglass
использует Unix flock, а интерактивный ari shell — SIGWINCH. Эти платформенные
ограничения не относятся к исправлениям протокола; Windows-программы здесь
проверены сборкой, а не запуском на Windows.

`go run golang.org/x/vuln/cmd/govulncheck@v1.7.0 -show verbose ./...`:
0 уязвимостей в вызываемых символах, 0 в импортируемых пакетах. Есть одно
уведомление на уровне модуля x/crypto —
[GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932), относящееся к неиспользуемому
пакету openpgp. Уведомление не исправляется обновлением версии (Fixed in: N/A)
и не затрагивает используемые Ariadne SSH/Ed25519 пути по результату этого сканирования.

Все проверки review после исправлений:

```sh
go test -race -run TestProtocolReview -count=1 -v \
  ./internal/pairing ./internal/relay ./internal/connector ./cmd/ariadne-connector
```

В исходном review этот набор запускался с тегом `protocolreview` и завершался
FAIL на пяти описанных дефектах. После исправлений все проверки PASS, сообщений
race detector нет; тесты теперь включены в обычный CI-прогон. Для одного только
защитного набора:

```sh
go test -race \
  -run 'TestProtocolReview(MITM|PairingReplaced|PairingConcurrent|PairingKE3)' \
  -count=1 -v ./cmd/ariadne-connector ./internal/pairing
```
